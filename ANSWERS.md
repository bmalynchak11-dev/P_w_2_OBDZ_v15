# Відповіді на питання практичної роботи OBDZ-P02

---

### Питання 1. Функціональні залежності та випадкові збіги (Набір 3)
1. **Записані залежності:**
   - `group_code -> curator`: кожна академічна група має рівно одного куратора.
   - `group_code subject -> hours teacher`: для конкретної групи та дисципліни призначається один викладач і визначається кількість годин.
   - `teacher -> subject`: закріплений викладач веде виключно одну дисципліну.
2. **Відкинуті збіги в даних:**
   - Залежності `subject -> hours` або `teacher -> hours` не існують: різні групи мають різну кількість годин з однієї дисципліни (наприклад, БД для G-11 має 60 год, а для G-12 — 54 год).
   - Залежність `subject -> teacher` також відкинута правилами: одну й ту саму дисципліну різним групам можуть викладати різні викладачі.

### Питання 2. Обґрунтування нормальної форми
Таблиця перебуває у формі **1NF**:
- Ключами-кандидатами є `(group_code, subject)` та `(group_code, teacher)`.
- Існує часткова функціональна залежність неключового атрибута `curator` від частини ключа `group_code` (`group_code -> curator`). Через наявність залежності від частини складеного ключа таблиця не відповідає вимогам 2NF і залишається у 1NF.

### Питання 3. Збереження залежностей і з'єднання без втрат
1. **Збереження залежностей:** Схема розкладена на три відношення:
   - `R1(group_code, curator)` — зберігає `group_code -> curator`.
   - `R2(teacher, subject)` — зберігає `teacher -> subject`.
   - `R3(group_code, teacher, hours)` — зберігає зв'язок навантаження групи та години.
   Усі залежності покриваються проєкціями відношень.
2. **З'єднання без втрат (Lossless Join):** Спільний атрибут між `R1` та `R3` — `group_code`, що є первинним ключем `R1`. Спільний атрибут між `R2` та `R3` — `teacher`, що є ключем у `R2`. З'єднання за ключами гарантує відновлення таблиці без появи хибних рядків.

### Рев'ю схеми колеги (Набір 1: Замовлення)
1. **Зауваження 1:** У правилах замовлення атрибути `price` та `product_name` повинні залежати від `product_id`, а не від пари `order_id product_id`, інакше утворюється надлишкова часткова залежність.
2. **Зауваження 2:** Необхідно стежити за розділенням даних покупця (`customer_id -> customer_name`) у 3NF, інакше зміна імені клієнта призведе до аномалії модифікації у всіх його чеках.

### Частина Б. Аналіз таблиці за темою проєкту
1. **Предметна область:** Журнал транзакцій фінансового обліку (`tx_id`, `tx_date`, `amount`, `user_id`, `user_email`, `category_id`, `category_name`).
2. **Правила та FDs:**
   - `tx_id -> tx_date amount user_id category_id`
   - `user_id -> user_email`
   - `category_id -> category_name`
3. **Нормальна форма:** Початкова таблиця знаходиться у **2NF**, оскільки ключ простий (`tx_id`), але присутні транзитивні залежності неключових полів через `user_id` та `category_id`.
4. **Декомпозиція:** Розбиття на `Transactions(tx_id, tx_date, amount, user_id, category_id)`, `Users(user_id, user_email)` та `Categories(category_id, category_name)` усуває дублювання, є з'єднанням без втрат і повністю зберігає всі залежності.
